Dataspace Management · mockup · phase 1 of 3

Participant management

Participant management keeps the record of every company of this onboarding service provider (OSP A): the company itself sees and keeps its data, its identifiers and its company roles; the staff of the OSP find companies, correct them, decide change requests and see the registration of each company at the core service provider (CSP). Behind it are two backend modules: c3-m1 Company Profile and c3-m2 CSP Connection (portal-backend-spec). Each view below is one screen of the portal with a configurator: switch the alternatives on the screen, copy the combination you like, and it becomes the decision of the view.

Your company

open

Every person of a company opens it from the rail (Participant management): the Company Admin (Erika) to check and keep the data of the company right, a Member (Max) to look up the BPN or an identifier. It replaces today's page "Your company" and links to the views 2 to 4.

The screen, with its configurator

Data from the spec

  • GET /api/c3-m1/companies/{companyId} (getCompany, view_company, scope company) → Company: name, shortName, address (street, houseNumber, postalCode, city, region, countryCode), identifiers[] (type, value, source), coreDataSource, coreDataVerifiedAt, bpn, status, companyRoles[], dataspaceName, activatedAt.
  • PATCH /api/c3-m1/companies/{companyId} (updateCompany, edit_company) with { shortName } only; null removes it. Errors: 409 field-locked, 409 invalid-state, 400 validation.
  • The open change request comes from GET …/change-requests (listOwnChangeRequests), first item with status OPEN.
  • States: read-only = Member without edit_company (buttons hidden by the permission of GET /me); not-found = 404 not-found (also another company); forbidden = 403 for Lieschen (Applicant).

Open questions

  • C3-M1: the UI may not decide that an INACTIVE company cannot be edited (6.6). Can Company return what the person may do now, for example allowedActions: [editShortName, attestationUpdate, changeRequest]?
  • C3-M1: Company has no deactivationReason for people of the company; the inactive state cannot say why (deactivated by the OSP or moved to another OSP).
  • C3-M1: openChangeRequestId is only in CompanyDetail (OSP). Also in Company, so the page needs one call instead of two?
  • C2-M5 / i18n: company role names are not in the API (only the key); the UI translates the keys, so a new role from the catalogue shows as its key until the UI is updated.

Change company data

open

Erika Mustermann, Company Admin of Beispiel Maschinenbau GmbH, comes here from "Your company" (button "Change company data", or "Verify again" in the verification banner) when the name, address or an identifier of her company is out of date. She chooses one of the two ways of C3-M1 6.6: verify again with the Business Wallet (applied at once) or request a change with supporting documents (decided by OSP A).

The screen, with its configurator

Data from the spec

  • POST /api/c3-m1/companies/{companyId}/attestation-updates (updateCompanyFromAttestation, edit_company, scope company): body AttestationUpdate.attestation (compact JWS from the EBW-Connector, fetched by the BFF with the scopes openid profile representation company attestation); response AttestationUpdateResult (changedFields, company), shown in the state "updated" (data of attestation T1: Beispiel Maschinenbau AG, Industriestraße 10, 70565 Stuttgart).
  • POST /api/c3-m1/companies/{companyId}/change-requests (createChangeRequest, edit_company, scope company), multipart/form-data: part data = ChangeRequestData (identifiers as the complete new list of DeclaredIdentifier {type, value}, optional name, address; required comment 1–1000), part documents (1–3 PDF/PNG/JPEG, ≤ 10 MB); response 201 ChangeRequest with status OPEN (state "submitted").
  • The current values ("Now") come from GET /companies/{companyId} (Company.name, address, identifiers[].source, coreDataSource); identifiers with source BUSINESS_WALLET are shown read-only.
  • Problem types shown: urn:c3-m1:problem:company-mismatch (fields [EBWOID]), attestation-used, attestation-required, change-request-open, document-invalid (one state button each).

Open questions

  • C3-M1: which fields may the company change on which way? Today the UI reads it from coreDataSource and the source of each identifier (a UX pre-check of 6.6; the API answers 409 attestation-required). Proposal: flags in Company, for example changeOptions: { attestation: [...fields], changeRequest: [...fields] }.
  • C3-M1: the installation can switch change requests off (CHANGE_REQUESTS_ENABLED) and sets the document limits (CHANGE_REQUEST_MAX_DOCUMENTS, CHANGE_REQUEST_MAX_DOCUMENT_BYTES). The UI cannot read them, so it shows the second card and the limits 3 / 10 MB without knowing. Needs a flag or GET /config.
  • C3-M1: no preview before the attestation is applied: 7.3 changes the data at once, so the UI can show the changes only afterwards. Should there be a dry run, or is "applied at once, then shown" the intended experience?
  • C3-M1: changedFields names fields without values; is the granularity name, address, EUID or single address parts (street, postalCode)? The UI compares the company before and after itself.
  • C5-M1 / BFF: can the EBW-Connector show its QR code inside the portal (cross-device, "QR code on this screen"), or does the person always leave to the EBW-Connector ("Continue to the EBW-Connector")? The BFF flow for a changed attestation (scopes, return URL) is not specified yet.
  • C3-M1: the identifier patterns (6.4) come from the reference data (masterDataFile); the UI cannot pre-check a VAT ID or LEI code before sending. Should the reference data be readable for the UI?
  • The mockup assumes no open change request in the state "loaded"; in the test data Erika has one open (LEI code), so a real submit gives 409 change-request-open. Should the screen warn before the form, from GET /change-requests?

Your change requests

open

Erika Mustermann (Company Admin) and Max Mustermann (Member, read only) of Beispiel Maschinenbau GmbH open this from "Your company" (the alert about the open change request, or the tab "Change requests") to follow their change requests, read why one was declined, and withdraw an open one.

The screen, with its configurator

Data from the spec

  • GET /api/c3-m1/companies/{companyId}/change-requests?page=&size= (listOwnChangeRequests, view_company, scope company): ChangeRequestPage (items, page, size, total), newest first; per item status, changes (name, address, identifiers), comment, documents[] (fileName, mediaType, sizeBytes only, no content), requestedBy, decisionReason, createdAt, closedAt; no decidedBy.
  • POST /api/c3-m1/companies/{companyId}/change-requests/{changeRequestId}/withdraw (withdrawChangeRequest, edit_company, scope company) → ChangeRequest with status WITHDRAWN; confirmed in a dialog.
  • "Now" in the details: GET /companies/{companyId} (current Company), compared with changes.
  • Test data: LEI code open (05 Nov), LEI code declined with the reason of Rolf Prüfer (04 Nov), EORI withdrawn (03 Nov).

Open questions

  • C3-M1: may this change request still be withdrawn? The UI shows "Withdraw" only for OPEN (a UX pre-check; the API answers 409 invalid-state). Proposal: a flag canWithdraw per item.
  • C3-M1 / C2-M2: requestedBy is a sub. The mockup shows the name ("Sent by Erika Mustermann"); the UI would need the name from C2-M2 or a requestedByName in the response.
  • C3-M1: there is no single read GET /companies/{companyId}/change-requests/{changeRequestId} for the company, so a link to one request (from a notification) has to search the list.
  • C11-M1: is the company notified of the decision (CompanyChangeRequestClosed), so the list updates live (SSE)?

Company roles

open

Erika Mustermann (Company Admin, edit_company_roles) opens this from "Your company" (link "Manage company roles") to see the roles of Beispiel Maschinenbau GmbH in Catena-X, add a role by accepting its terms, or remove one. Max Mustermann (Member) sees the same page read only.

The screen, with its configurator

Data from the spec

  • GET /api/c3-m1/companies/{companyId}/company-roles?lang=en (listCompanyRolesOfCompany, view_company, scope company): CompanyRoleState[] with companyRole, assignableBy, status (NONE, REQUESTED, ACTIVE, INACTIVE), description, agreements[] = AgreementConsent (agreementKey, version, name, documentUrl, consentStatus, consentedVersion, consentedAt).
  • POST /api/c3-m1/companies/{companyId}/company-roles (addCompanyRole, edit_company_roles, scope company): CompanyRoleAdd = companyRole + consents[] (AgreementRef: agreementKey, version) — one checkbox per term; 400 consent-missing (missing), 502 upstream-error (terms of C1-M2 not readable).
  • DELETE /api/c3-m1/companies/{companyId}/company-roles/{companyRole} (removeCompanyRole, edit_company_roles, scope company), confirmed in a dialog; 409 last-role when the last active role would go (state "last-role").
  • Terms of the test data (C1-M2 14.3): terms-active-participant, security-regulations, terms-app-provider, terms-service-provider, all version 1.0.

Open questions

  • C3-M1: CompanyRoleState has a description but no display name; the UI translates the key (roles.ACTIVE_PARTICIPANT). Should the response carry the localized name, as the catalogue of C1-M2 does?
  • C3-M1: may this role be added or removed now? The UI derives it from assignableBy and status (a UX pre-check; the API decides, for example 409 last-role, role-not-assignable, invalid-state). Proposal: flags canAdd and canRemove per role, so "Remove" is not offered for the last role.
  • C3-M1: removing a role sets the consents to its terms INACTIVE unless another active role needs them (6.5). Should the confirmation name which terms are withdrawn, and should the API return that?
  • C3-M1 / C10-M1 / C8-M1: removing APP_PROVIDER or SERVICE_PROVIDER does not check offers or subscriptions (7.9). Should the UI warn, and from which module?
  • C3-M1: a new version of terms keeps the key; re-consent is not part of version 0.2 (OP-11). The page shows "Version 1.0 accepted"; how should it show an accepted version that is older than the active one?

Companies

open

OSP staff (Rolf Prüfer, OSP Reviewer; Otto Normalverbraucher, OSP Admin) open it from participant management to find any company of the installation, from the application to the deactivation, and open its record.

The screen, with its configurator

Data from the spec

  • GET /api/c3-m1/osp/companies (listCompanies, x-permission: view_companies, scope osp): query status (repeatable), name (contains, case-insensitive), bpn, hasBpn, companyRole (active roles only), coreDataSource, page, size; sorted by createdAt descending.
  • Response CompanyPage { items, page, size, total } of CompanySummary: id, name, status, bpn, coreDataSource, countryCode, companyRoles (active), createdAt.
  • The drawer alternative shows more than the summary (address, identifiers, open change request): it calls GET /api/c3-m1/osp/companies/{companyId} (getCompanyDetail, view_companies) when it opens.
  • Errors: 403 urn:c3-m1:problem:forbidden (for example a Company Admin), 400 urn:c3-m1:problem:validation (invalid filter value).

Open questions

  • One search field for name or BPN: the API has two parameters (name contains, bpn exact). Does the UI decide by the BPN pattern which one to send, or can C3-M1 add a combined q? (C3-M1)
  • Other sort orders (name, status) and a sort parameter are not in the spec; only createdAt descending. Enough for OSP staff? (C3-M1)
  • CompanySummary has no open change request and no "needs attention" flag; a column "open change request" would need openChangeRequestId in the summary. (C3-M1)
  • The drawer needs a second call per company; is the summary plus a link enough, or should the summary carry the address? Decide with the drawer alternative.

6

Company

open

OSP staff open one company from the list of companies, from a review case or from a change request: to see its full record, to correct its data after a hint (OSP Admin) or to deactivate it (OSP Admin), and to see how the core service provider knows it (C3-M2).

The screen, with its configurator

Data from the spec

  • GET /api/c3-m1/osp/companies/{companyId} (getCompanyDetail, view_companies, scope osp): CompanyDetail = Company (name, shortName, address, identifiers[].source, coreDataSource, coreDataVerifiedAt, bpn, status, companyRoles, dataspaceName, createdAt, changedAt, activatedAt) plus applicationId, verificationRef, bpnAssignedAt, deactivationReason, rejectedAt, deactivatedAt, reactivatedAt, openChangeRequestId. 404 not-found.
  • PATCH /api/c3-m1/osp/companies/{companyId} (correctCompany, manage_companies): CompanyCorrection name, shortName, address (with countryCode), identifiers (the complete new list of DECLARED ones), reason (1–500, required). Name or address of an EBW company → source MANUAL, verificationRef empty (shown in the form). Errors 409 field-locked with fields (for example countryCode after the BPN), 409 invalid-state, 400 validation.
  • POST /api/c3-m1/osp/companies/{companyId}/deactivate (deactivateCompany, manage_companies): Reason reason (1–500, audit log only). The dialog lists the consequences of FRAMEWORK 5.4. Response CompanyDetail with status INACTIVE, deactivationReason MANUAL.
  • C3-M2: GET /api/c3-m2/companies/{companyId} (getCspRegistration, view_csp_registration, scope osp, OSP Admin only): status, bpn, did, membership, registeredAt, updatedAt. Hidden for the OSP Reviewer (no permission), as in the state read-only.
  • Open change request: openChangeRequestId → link to the review (GET /osp/change-requests/{id}, review_company_changes).

Open questions

  • The UI shows "Correct data" for ACTIVE and REQUESTED and "Deactivate" only for ACTIVE: that is a rule of 6.1 and 7.12/7.13. C3-M1 should return the allowed actions as flags (for example canCorrect, canDeactivate) so the UI decides nothing. (C3-M1)
  • Which fields are locked (country after the BPN, identifiers from the Business Wallet) is rule 6.6. The form shows the lock from data; C3-M1 should return the locked fields (for example lockedFields) instead of the UI knowing 6.6 and only learning it from a 409 field-locked. (C3-M1)
  • The deactivation reason is only in the audit log. Should OSP staff see who deactivated and why on this page? There is no read operation for the audit log. (C3-M1)
  • Company roles: OSP staff cannot change them (6.6, "no"). Is that intended, also for removing a role after a breach? (C3-M1)
  • The page combines two modules. Should C3-M1 CompanyDetail carry a short CSP status, or is the second call to C3-M2 the intended way? (C3-M1, C3-M2)

CSP registration

open

The OSP Admin (Otto Normalverbraucher) opens it from the record of a company to see how the core service provider knows the company: whether it is registered with a BPN and OSP A as home OSP, whether its DID is in the BPN → DID directory, and whether it is a member of the dataspace. It is the only screen of C3-M2.

The screen, with its configurator

Data from the spec

  • GET /api/c3-m2/companies/{companyId} (getCspRegistration, x-permission: view_csp_registration, scope osp): CspRegistration companyId, bpn, status (PENDING, REGISTERED, FAILED, TRANSFERRED_AWAY), failureReason (for example REGISTERED_AT_OTHER_OSP), did, membership (NONE, REGISTERED, DEREGISTERED), registeredAt, updatedAt.
  • Errors: 404 urn:c3-m2:problem:not-found (company without registration, for example before the approval), 403 urn:c3-m2:problem:forbidden (OSP Reviewer), 401 unauthorized.
  • The company card (alternative "Company card from C3-M1") reads GET /api/c3-m1/osp/companies/{companyId} (view_companies): name, address, status.
  • The three parts (registered, DID, membership) are read from the fields above; the UI does not say what runs next.

Open questions

  • The response has no home OSP (homeOspId, homeOspName) and, for TRANSFERRED_AWAY, not the new OSP; the screen can only say "this installation" when REGISTERED. Add them to CspRegistration? (C3-M2)
  • No history: there is no list of the calls and notifications (audit_entry, csp_notification) for OSP staff, so "when was the DID entered" or "when did the transfer arrive" cannot be shown. (C3-M2)
  • No action for staff: after FAILED only Process Orchestration can run register-company again. Should the OSP Admin be able to retry, or see the process (C12-M1)? (C3-M2, C12-M1)
  • No list endpoint: an overview "all companies at the CSP" (for example all PENDING or FAILED) needs one call per company. Add GET /api/c3-m2/companies?status=? (C3-M2)
  • failureReason is free text from the CSP; the UI translates known values (REGISTERED_AT_OTHER_OSP). Can the spec list the possible values as an enum? (C3-M2)
  • The connectors entered in the discovery (csp_connector) are not readable; show them here or only in C6-M1? (C3-M2, C6-M1)

Change requests to review

open

OSP staff with review_company_changes (Rolf and Renate, OSP Reviewer; Otto, OSP Admin) open it from Participant management or from a notification about a new request. They work the oldest request first.

The screen, with its configurator

Data from the spec

  • GET /api/c3-m1/osp/change-requests?status=OPEN&companyId=&page=&size= (listChangeRequests, review_company_changes, scope osp) → ChangeRequestPage { items, page, size, total }, sorted by createdAt, oldest first.
  • Per row from ChangeRequest: companyName, changes (name, address, identifiers; the changed fields are the summary), documents.length, status, createdAt (waiting time), closedAt.
  • The source of the core data under the company name needs GET /osp/companies/{id} per company (or the list of 7.10).
  • States: empty = no open request; forbidden = 403 for a Company Admin; error = 400 validation for a bad filter.

Open questions

  • C3-M1: the counts in the status tabs need one call per status. Can the page return counts per status (totals), or do we drop the counts?
  • C3-M1: ChangeRequest has companyName but not coreDataSource; add it, so the list shows which requests touch Business Wallet data without a call per company?
  • C11-M1 Notifications: is there a notice to OSP staff on CompanyChangeRequestSubmitted? The empty state promises one.
  • Live update (SSE) of the list when a colleague decides a request: which event stream does the UI subscribe to?

Review change request

open

The reviewer (Rolf) opens one change request from the list: compares the current data with the requested data, reads the reason, opens the supporting documents and approves or declines with a reason that the Company Admin sees.

The screen, with its configurator

Data from the spec

  • GET /api/c3-m1/osp/change-requests/{changeRequestId} (getChangeRequest, review_company_changes, scope osp) → ChangeRequestDetail: changes, comment, documents[] (id, fileName, mediaType, sizeBytes), requestedBy, status, createdAt and company (name, address, identifiers, coreDataSource, status) for the comparison.
  • GET …/documents/{documentId} (getChangeRequestDocument): the file with Content-Disposition: attachment; every read is in the audit log (the page says so).
  • POST …/approve (approveChangeRequest) with optional comment (≤ 1000, audit log only); POST …/decline (declineChangeRequest) with required reason (1–1000, shown to the Company Admin).
  • States: approved and declined = the results; same-person = 409 same-person (four-eyes principle); attestation-required = 409 when the company verified with its Business Wallet in the meantime; not-found = 404.

Open questions

  • C3-M1: only the sub of the requesting person is returned (requestedBy). Shown here as a name: does the UI resolve it through C2-M2, or does C3-M1 return a display name?
  • C3-M1: the UI cannot know before the call that the reviewer is the requester (409 same-person). Can ChangeRequestDetail return canDecide (or the reason why not), so the buttons are not shown?
  • C3-M1: the preview of a document needs an inline variant of 7.16 (Content-Disposition: inline), or the UI shows a download only.
  • C3-M1 / C12-M1: after the approval, core data goes to the CSP (C3-M2 update-company). Should the page show that this step ran?
